# 实施路线

实施路线以可验证的业务结果组织，不以引入多少框架为目标。

## M0：项目立项

目标：建立真实、可审查的项目起点。

- 明确产品范围和暂不实现的内容。
- 创建 GitHub 仓库和基础文档。
- 约定代码提交和验证规则。
- 创建第一个里程碑和任务清单。
- 产品范围审阅完成后，才初始化最小 Go 服务。

退出条件：

- 仓库说明了业务问题、参与者、第一条业务闭环、正确性约束和当前进度。
- 第一批实现任务能够分别完成和独立验证。

## M1：有依据的知识回答

目标：只能依据当前租户有权使用的有效知识回答客服问题。

计划切片：

1. 最小 Go 服务和健康检查接口
2. 租户身份边界
3. 文档及版本生命周期
4. 文档解析和切块
5. 向量生成与租户范围检索
6. 带引用的回答生成
7. 无依据和依赖故障处理
8. 第一套离线评测数据

## M2：客服业务流程

目标：把知识回答和受控的业务操作连接起来。

计划能力：

- 客服会话状态
- 订单查询
- 退款资格判断
- 工单创建
- 工具权限、确认、幂等和审计
- 带有已验证摘要的人工客服接管

## M3：生产化能力

目标：让系统质量和失败行为可以观测、复现和持续改进。

计划能力：

- 流式回答
- 检索与回答的回归评测
- 提示注入和数据隔离测试
- 模型服务超时、重试和降级策略
- 延迟、Token、成本和错误指标
- 在实际工作流需要时引入异步文档处理
- 容器化本地与部署环境
